# State Reconcile 01

**2026-11-09 · Lua 5.4 PASS для политики · read-only сеанс завершён · применение маски BLOCKED.** База `721e60f39fc1bf942ae34611472aab1100707b83`. Ветка `research/scabbard-state-reconcile-01`.

## Почему меняем механизм

[Integrated 04](SCABBARD_INTEGRATED_21.md) дал визуальный PASS шести целей для клинков с молотом. При замене через меню срок истёк раньше выхода старого актора. [05](SCABBARD_INTEGRATED_22.md) сохранял ожидание до refresh по EndPlay, но при следующем игровом переходе оно потерялось. Поздний helper был гипотезой причины. [06](SCABBARD_INTEGRATED_23.md) успешно применил текущий native registry к меню, но обратный переход с поздней второй рукой не запустил ожидание. [07](SCABBARD_INTEGRATED_24.md) отделил регистрацию события от полноты комплекта и прошёл оба направления меню. Новая комбинация молот → посох в комбо всё ещё оставляла `drawPending`. [08](SCABBARD_INTEGRATED_24.md#integrated-08--адресная-регрессия-комбо-смены) добавил ещё одно имя skill, с PASS в Lua и открытым игровым результатом.

Имена skills обеспечивали ранний release, защёлки защищали от позднего Sheath, специальное ожидание меню переживало выход старого held, а checks вспомогательных акторов старались отличить ещё живой комплект от сменившегося. Некоторые из этих проверок были обязательны для безопасности. Сложность росла там, где допуск к hide зависел от восстановления маршрута и точного порядка событий. Native registry впервые дал альтернативу части этих зависимостей, а новый контракт убрал требование начинать отсчёт от конкретного события.

DevRules уже требовали сравнения механизмов и повторного выбора при росте сложности. Эти правила помогали ограничить риск каждого исправления, но оставляли неявным вопрос, можно ли получить искомый результат из текущего состояния. Дополнение в `ENGINEERING_RULES.md` ставит этот вопрос в существующий checkpoint и связывает его с ростом частных исключений. Оно применимо и к интеграциям с push-уведомлениями, кэшам и UI. Частота наблюдения остаётся выбором по данным.

## Проверка источника и граница готовности

Доказательства thunk и Lua-доставки приведены в [Integrated 06](SCABBARD_INTEGRATED_23.md), поздняя вторая рука и живое копьё — в [Integrated 07](SCABBARD_INTEGRATED_24.md). Переносимых новых наблюдений об игре пока нет. [Общий Research](https://github.com/NikichMods/Asterigos-Research/blob/main/docs/RESEARCH_INDEX.md) даёт контракт delayed GameThread callbacks и его ограничения.

| Источник | Что он даёт | Что остаётся проверить |
| --- | --- | --- |
| `GetInUseWeaponType(pawn, 0/1)` | Текущие два выбранных типа на проверенных путях | Доступность и полнота в меню, при пустом наборе, для остальных семейств |
| `GetWeaponObject(pawn, type, slot)` | Живые экземпляры по типу и слотам рук, в сочетании с выбранными типами | Позднее появление offhand, полный набор ShieldSword/Bracer, старый видимый held вне выбранного набора |
| `GetInHandWeaponType(pawn)` | Активный тип или `None=7`; помог исключить ещё активную руку при смене | None сам по себе не различает stowed, drawing до commit, stowing, пустую экипировку и промежуточные состояния |
| Текущие actor mode, owner/root/mount, stock held/blade/sheath и skill activity | Кандидат на дополнительное подтверждение снимка; формы полей заимствованы из проверок Integrated | Нет доказательства, что снимок замечает все drawing/stowing, каждый видимый outgoing held и краткие переходы между опросами |

Для будущей записи нужны достоверный локальный контекст, обе актуальные native записи слотов и обязательные части оружия, отсутствие held и перехода, совпадение текущих целей с доказанными stock owner/root/socket/asset, право записи, readback и обратимость. Независимость от штатных writers остаётся существенным пробелом. Общий `SetHiddenInGame` на `scabbard_a/b` не охватывает отдельные акторы и используется игрой. Поэтому исследуем композицию getter + текущие проверки, с одним общим pre как возможной инвалидацией. Путь через историческую реконструкцию несёт уже наблюдавшиеся сбои. Низкоуровневый native hook имеет смысл оценивать, только если read-only проверка покажет конкретный пробел, который нельзя закрыть доступным host-сигналом.

| Семейство | Доказательство на входе | Готовность в новой ветке |
| --- | --- | --- |
| Меч и щит | Enum и cooked shield; есть отдельный sword BP | Наблюдение слотов. Состав пары, режим и held/mount в игре открыты |
| Молот | Игровой hide/show и stock цепочка для ранее проверенного набора | Модельный stowed, нужен замер раннего pre и непрерывности |
| Браслеты | Enum и cooked индексы акторов | Наблюдение слотов. Геометрия ножен и живая конфигурация не установлены |
| Посох | Игровой hide/show и выбранный actor; два способа переключения различаются по pre | Модельный stowed, проверить общий pre на комбо без классификации |
| Парные клинки | Native main/off и прошедшие смены в меню, offhand появляется позже | Модельный stowed только с main + off; проверить отсутствие ложного допуска до появления off |
| Копьё | Правый native slot, root на `scabbard_a`, невидимый held в Sheath и pre за 165 мс до InHand в одном опыте | Наблюдение слотов. Визуальное начало движения, другие маршруты и полнота ещё открыты |

## Исследовательский код и стоимость

[reconcile.lua](../research/scabbard-state-reconcile-01/Scripts/reconcile.lua) хранит только identity, начало и время последнего достоверного наблюдения. Выход из stowed, разрыв наблюдения, смена identity, lifecycle или generic pre сбрасывают окно. После 3000 мс требуется свежее чтение в том же callback. Ни старый Sheath-таймер, ни `drawPending`, `observedDraw`, маршруты menu/button, имена анимаций, боевой getter и ожидание EndPlay не участвуют. Безобидный helper вне снимка не меняет ключ.

[Наблюдатель](../research/scabbard-state-reconcile-01/Scripts/main.lua) использует один повторяющийся game-thread callback с задержкой 100 мс. На выборку приходится один hand getter, два in-use getters, до четырёх lookup экземпляров, два skill-state getters и ограниченные чтения контекста/компонентов. В зрелом окне выполняется повторное чтение. Нет широкого скана компонентов, поиск HUD ограничен восстановлением контекста с интервалом около секунды. Верхняя номинальная частота около 10 наблюдений/с, до 20 чтений снимка/с с перепроверкой, без гарантии реальной длительности кадра. STOP сообщает число выборок и максимальный интервал. Без раннего события задержка обнаружения после доступного getter-изменения номинально около одного интервала плюс кадр/нагрузка. Это оценка структуры вызовов, стоимость на кадр ещё не измерена.

Часы `GameplayStatics:GetRealTimeSeconds` уже использовались на UE4.27 в [HildaSoftLight live tuner](https://github.com/NikichMods/HildaSoftLight/blob/main/docs/LIVE_TUNER.md). Проба использует их в пределах текущего мира, сбрасывая окно при смене поколения, LoadMap, регрессии часов и пропуске более 250 мс. 100 и 250 мс — исследовательские параметры. Даже при меньшем пропуске непрерывность требует доказательства, что значимые короткие переходы либо видимы в снимке, либо инвалидируют окно общим host-сигналом. `WOULD_HIDE` отмечает гипотезу модели для трёх семейств, а не разрешение на запись. Отсутствует проверка полного каталога 15 и outgoing held вне текущих слотов. Установленного write-кандидата этой архитектуры нет.

Lua 5.4 через Lupa 2.8. `lua test.lua` из каталога исследования: **1030 assertions PASS**. Проверены граница 2999/3000, повторные снимки, прерывания в разных местах окна, быстрый новый kit, исчезновение offhand как UNKNOWN, drawing после зрелости, смена между чтениями, generic pre без draw, пропуски наблюдения, регрессия часов, пустой набор и новый pawn. Это тест политики на независимо поданных входах. Конфликт writers, частичный rollback и защита world/held на write-path остаются проверками будущего write-кандидата. Исторические PASS из Integrated относятся к их исходникам.

`lua test_observer.lua`: **PASS** на подменённых host API. Проверены отсутствие допуска для шести неполных наборов, положительный stock-снимок молота, блокировка при видимом held, local/foreign pre, LoadMap, STOP, единственный loop и игнорирование callback старого сеанса после повторного START.

## Один объединённый игровой сценарий

После отдельного разрешения на установку и проверки точных хэшей, с закрытой игрой, оставить один активный наблюдатель. Использовать существующий сейв со штатными вариантами всех шести семейств. **Ctrl+Alt+F7** начинает наблюдение, **Ctrl+Alt+F8** останавливает. Проба не пишет игровое состояние. Сопоставить журнал с видеозаписью или визуальными отметками начала движения. `SKILL_PRE` использует отметку последней выборки, время самой доставки брать из timestamp журнала.

1. По очереди для всех шести семейств дать оружию убраться, дождаться как минимум трёх секунд устойчивого состояния и вынуть. Сопоставить выбранные слоты, нужные экземпляры, held/комплект, `SKILL_PRE` и первый видимый кадр draw. Отдельно отметить любое `WOULD_HIDE` во время видимого перехода и отсутствие доказанного состава. Меч со щитом, копьё и браслеты ожидаемо не получают модельного допуска.
2. Пройти смену Staff → Dual через меню без атаки с поздней второй рукой, затем Cudgel → Staff второй кнопкой во время комбо. Проверить, что outgoing held и входящий неполный комплект распознаваемы до допуска. Повторить draw в пределах окна и выполнить один неоружейный skill в stowed. Отметить, был ли pre при отсутствии draw и когда наблюдатель снова допустил бы hide.
3. Загрузить существующий сейв, один раз дождаться stowed, затем STOP. Проверить новый identity, новый интервал, отсутствие выборок после STOP, наблюдаемую задержку и стабильность в простое. Граница успеха пробы — журнал позволяет принять или опровергнуть достаточность снимка и применимость общего pre без подмены фазы именами skills.
4. После закрытия gate тот же сценарий для будущего write-кандидата дополнить фактической проверкой видимости ножен с начала draw, отсутствия пропажи активного оружия и дублей, hide после 3000 мс, отсутствия ложного появления и восстановлением своих масок при STOP с активным подавлением и при reload. Любая остаточная маска, чужая запись или исчезнувшее held блокируют приёмку.

## Игровой сеанс 2026-11-09

Загрузился State Reconcile 01 из `ebfd9b13c4a31959158f85e7e5b75ab7beae3167` на UE4SS `83330635`. Оба установленных Lua совпали с хэшами выше. SHA-256 приватного журнала `5cfc3b021fde639c3528ee1a94b268c32a966febcf3abfdfcb9c1e698f28c705`. STOP: `samples=3295 max_gap_ms=195.8 writes=0`. Максимум относится к соседним доступным отметкам часов, исключая разрыв контекста/смену мира. Стоимость на кадр не измерялась.

- **Политика времени:** десять `WOULD_HIDE`, через 3018,3–3032,9 мс по часам мира от первого соответствующего STOWED. Только в проверенных сочетаниях молота, посоха и парных клинков. При повторном draw посоха примерно через 1,52 с от STOWED допуска не было. При reload виден разрыв контекста, затем новое окно на новом pawn. STOP подтверждает завершение наблюдения без записей.
- **Смены:** в участке меню посох в руке → неопределённость → полный Dual main/off с молотом → `WOULD_HIDE` без новой атаки. Промежуточного снимка с одним main и задержавшимся off в этом участке нет. Комбо молот → посох зарегистрировано, после него вновь наблюдался STOWED. Журнал не показывает, оставался ли физически видимый старый held вне выбранных слотов.
- **Все шесть:** переходы в native DRAWN видны для типов 0–5. В устойчивом снимке щита появились `HildaShield_BP_C` на `scabbard_a` и `HildaSword_BP_C` на `scabbard_b`, оба штатных held с `bVisible=false`. Копьё повторило правый слот и stowed на `scabbard_a`. У браслетов правая native запись указывает на `HildaBracelet_BP_C` с mode 1, `bracelet_r_hand` и видимым `hilda_bracelet` при hand=None. Нужна отдельная проверка роли штатной геометрии браслетов в данных адаптера. Эти три семейства оставались UNKNOWN при hand=None.
- **Ранний сигнал:** во всех шести наблюдаемых типах есть `SKILL_PRE` раньше первого sampled DRAWN. Для обычных stowed → drawn в журнале расстояние между отметками порядка 149–283 мс. Это сравнение с выборкой getter, а не с первым видимым кадром. Пользователь уточнил, что выбранный астральный навык действительно вынимал оружие. Это положительная проверка draw; случай навыка без вынимания остаётся открытым.

Сеанс подтверждает пригодность политики времени и части текущего снимка. Для допуска write нужны адресные доказательства достаточной ранности сигнала, состояния outgoing held, границ stock-целей и канала записи с безопасным rollback. Сначала проверить, можно ли дополнить снимок узким чтением старого комплекта и сопоставить pre с первым видимым draw в уже освоенном наборе. Если этот сигнал приходит поздно или не отделяет реальный draw от действий в stowed, выбирать другой host-сигнал до подключения маски. Полный шестисемейный прогон повторно для этого вопроса не нужен.
